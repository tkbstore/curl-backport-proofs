# 手順書: Debian の curl のセキュリティパッチに、人の判断なしで判定を付けて公開する

作成: 2026-10-28
前提: `PROTOCOL-trixie-batch.md` と `RESULTS-trixie-batch.md`（14件を人が介在して回した）。この手順書は、そこで人が判断した箇所をすべて規則に置き換える。

## 1. 何のためか

使い手は Debian の curl の保守者。新しいセキュリティのバックポートが salsa に入ったら、
そのバックポートが上流の修正と同じ性質を持つかの判定を、人を介さずに作って公開する。
判定は規則と、Lean のビルド・`#print axioms` の機械的な確認だけで決める。判断する人は置かない。結果は既定で公開する。

## 2. 検知

- 見る場所: salsa.debian.org `debian/curl` の各リリースのブランチ（まず `debian/trixie`）の `debian/patches/`
- 対象: 前回見たコミットから増えた、または中身（sha256）が変わった `CVE-*.patch`。前回見たコミットと処理済みのパッチの sha256 は、公開リポジトリの `state/` に記録する

## 3. 規則（人に回さない）

### 3.1 上流の修正の特定

`https://curl.se/docs/<CVE>.json` の `affected[].ranges[]` のうち `type` が `GIT` のものの `fixed` を修正後（U1）、その親を修正前（U0）とする。
`fixed` が無い、または複数ある場合は、判定「上流の修正を特定できない」として公開する。

### 3.2 大きさ

テストと文書を除いて、C の `.c` が1ファイルで、差分が40行以下のものだけを証明する。
それ以外は判定「対象外（大きさ）」として、変更したファイルと行数を添えて公開する。
C のファイルを1つも変えていないパッチ（文書だけなど）は、判定「C の変更が無い」として公開する。
CVE が複数のパッチ（`_1`・`_2` など）に分かれている場合は、パッチごとに扱う。

### 3.3 D0 と D1

- D1: 8.14.1 に、Debian の series でこのパッチまでを順に当てたもの
- D0: 8.14.1 に、series でこのパッチの直前までを当てたもの
- 当たらないパッチがあれば、判定「パッチが当たらない」として公開する

### 3.4 仕組みの比較（証明の前に機械で決める）

上流の修正コミットが C のファイル（`.c`・`.h`。`tests/`・`docs/` を除く）に足した行のうち、
Debian のパッチが足した行のどれかと `difflib` の一致の度合いが 0.8 以上になる行の割合（`up_in_deb`）を測る（`auto/mechanism.py`）。
- 0.5 以上なら、証明に進む
- 0.5 未満なら、判定「上流と仕組みが違う」として、割合と両方の足した行を添えて公開する

境界の決め方: trixie の14件で、証明できた13件の `up_in_deb` は 0.80〜1.00、上流と仕組みが違った CVE-2026-5773 は 0.00 だった（2026-10-28 の実測）。
0.5 はその間に置いた。この14件で決めた境界なので、独立には確かめていない。次に流す件（bookworm など）が最初の検証になる。
最初の案（変わった関数の名前の集合を比べる）は使わない。上流で関数が分割・改名された CVE-2025-10148・CVE-2025-14524・CVE-2026-8927 を、
証明できたのに「仕組みが違う」と判定してしまうため。

### 3.5 性質

- 証明の前に `cases/<CVE>.md` に P1・P0（日本語と Lean の定理の形）・対象の関数・構成・仮定する外部仕様を書き、コミットしてから証明に入る
- 性質のコミットの後で前提・仕様・述べ方を変えたら、変えたことと理由を記録し、判定の「性質の変更」の欄を「あり」にする。変えること自体は許す
- 許す変更は C1 の §4 と同じ

### 3.6 判定

| 判定 | 条件 |
|---|---|
| 同じ性質 | U1・U0・D1・D0 がすべて成立し、§4 の機械的な確認を通る |
| 証明できず | 上限（1件 4時間・`lake build` 80回）に達した。どこまで成立したかを添える |
| 上流と仕組みが違う | §3.4 |
| 対象外（大きさ） | §3.2 |
| 上流の修正を特定できない | §3.1 |
| C の変更が無い | §3.2 |
| パッチが当たらない | §3.3 |

判定には、主張の範囲（すべての入力か、場面を絞ったか）と、仮定した外部仕様の数を必ず添える。

### 3.7 件の記録（機械が読む形）

`cases/<CVE>.md` と並べて `cases/<パッチ名から .patch を除いたもの>.json` を置く（例 `cases/CVE-2026-1965_2.json`）。§4 の確認と公開はこれを読む。
trixie の14件はこの形で `cases/` の直下にある。自動で回す件は、同じ CVE が複数のリリースに出るので `cases/<リリース>/`（例 `cases/bookworm/CVE-2025-14819.json`）に置き、
Lean のモジュールの頭も `Deb<リリース>`（例 `DebBookworm2025_14819`）にする。

### 3.8 証明のジョブ（`auto/prove.py`）

`auto/build.py` の出力1件ごとに、worktree を1つ作って `claude -p` に §3.5〜§4 を行わせる（指示は `auto/prove-prompt.md`）。名前（件の記録・モジュール・build の case-id）はジョブの前に決めて渡す。
- `lake build` の回数: `lean/build.sh` が、環境変数 `BUILD_LIMIT` の回数に達したら走らない
- 時間: 上限を過ぎたらプロセスごと止める
- 判定: ジョブが「同じ性質」と書き、上限の内で終わり、`auto/check.py` が合格としたときだけ「同じ性質」。それ以外は「証明できず」と理由。結果は `cases/<リリース>/<パッチ>.prove.json`
- 限界: `build.sh` を通さずに `lake` を打つことは止められない（指示で禁じているだけ）

```json
{
  "patch": "CVE-2026-4873.patch",
  "cve": "CVE-2026-4873",
  "branch": "debian/trixie",
  "debian_commit": "c2a97b9ea5…",
  "upstream_fixed": "507e7be5…",
  "verdict": "同じ性質",
  "scope": "すべての入力 | 場面を絞った（理由を1行）",
  "property_changed": false,
  "external_specs": {"U1": 1, "U0": 1, "D1": 1, "D0": 1},
  "lean_modules": ["Deb2026_4873"],
  "theorems": {"U1": ["Deb2026_4873C.P1_C"], "U0": ["Deb2026_4873C.P0_C"],
               "D1": ["Deb2026_4873C.P1_D"], "D0": ["Deb2026_4873C.P0_D"]},
  "d_functions": {"D1": ["Deb2026_4873_d1.f_url_match_ssl_use"], "D0": ["Deb2026_4873_d0.f_url_match_ssl_use"]}
}
```

`verdict` は §3.6 の表の文言のどれか。`scope` は、P1・P0 の文に、その件のために前提を足したり対象の関数の一部だけを扱ったりしたなら「場面を絞った（理由を1行）」、していなければ「すべての入力」。定理が無い件は null。`property_changed` は、性質をコミットしたあとに性質の文を変えたか（定理が無い件は null）。`theorems` は判定の根拠になる主な定理の完全な名前。`d_functions` は D の定理が指すべき Clight の関数の完全な名前。

### 3.9 性質の読み直し（`auto/review.py`）

Lean が保証するのは「書いた性質が成り立つ」までで、その性質が脆弱性を捉えているかは保証しない。そこで証明のジョブの後に、別の `claude -p` に性質を読ませる。
- 渡すのは `cases/…md` の「結果」の節より前だけ（成否を知らせない）と、curl の advisory・Debian のパッチ・上流の修正・4つの C ファイル。道具は読み取りだけ
- 問いは4つに固定する: P1 が修正後に脆弱性が起きないことを述べているか、P0 が修正前に起きる入力があることを述べているか、前提の絞り込みが脆弱性の経路を外していないか、外部仕様の仮定が脆弱性に関わる振る舞いを決めてしまっていないか
- 答えは `prove.json` の `review` に入り、`VERDICTS.md` の Read-back の列に「指摘なし／指摘あり（問いの名前）／読み直しできず」として出る
- **判定は変えない**。読む側も AI なので、判定を覆す権限は与えず、指摘をそのまま公開する

### 3.10 P0 を修正後の関数で述べ直す（`p0_on_fixed`）

P0 が修正後の関数でも成り立つなら、P0 は修正の前と後を見分けておらず、修正前にバグがあることを示していない。これは読ませなくても Lean で確かめられる。
- 述べ方: P0 の定理の関数と仕様を修正後のもの（U1、D1）に置き換える。修正後にだけある引数やメモリ（足された欄など）は、P0 の入力と同じ量化子（∃ なら ∃）の側に入れる。
  事後条件（悪い出来事）は P0 のまま変えない
- 成り立ったら、件の記録に `"p0_on_fixed": "成立"` と、その定理を `theorems.P0_on_fixed` に書く。§4 の確認を他の定理と同じく受ける。
  試して成り立たなかったら `"示せず"`。これは P0 が見分けることの証明ではない。試していなければ欄を置かない
- `VERDICTS.md` の P0 on fixed の列に出す。**判定は変えない**（§3.6 の「同じ性質」の条件は4つの定理が成り立つことで、これは変わらない）
- 実例: trixie の CVE-2025-14819。`mb->no_partialchain` も 1 を選ぶと修正後の関数も FALSE を返す（`Deb2025_14819X.P0_on_after`、1回目の build で成立）。
  読み直し（§3.9）は bookworm の同じ形の P0 には指摘を出し、trixie には出さなかった

## 4. 機械的な確認

- 統合したツリーで `lake build` が成功する
- 件の主な定理の `#print axioms` が、Lean の標準の3つと `CC.externalFunctionsSem`・`CC.inlineAssemblySem` の部分集合である
- `sorry`・`admit`・`native_decide`・`bv_decide`・`axiom` の宣言が無い
- D の定理が D 側の関数（`*_d1`・`*_d0`）を指す（`#check`）

どれかを通らなければ、判定は「同じ性質」にしない。

## 5. 公開

判定・`cases/<CVE>.md`・証明・翻訳単位を、公開リポジトリに自動でコミットして push する。人の確認は挟まない。

- 1回の実行: `auto/run.py`。リリースごとに detect → `mechanism.py --judge` → 規則で決まった件は記録、残りは `build.py` と `prove.py`（1回で `--max-proofs` 件まで）。
  証明のブランチはパイプライン専用の checkout（ブランチ `auto/pipeline`）にマージする。人が作業する checkout では動かさない
- 公開: `publish/publish.py`。`export.py` の写しで公開リポジトリの中身を置き換え、`state/`・`VERDICTS.md`・`verdicts.json` を足して push する
- `state/` に入れるのは、その回で判定まで行ったパッチだけ。`--max-proofs` で残した件は次の回にもう一度検知される
- 定期実行: `auto/scheduled.sh install <公開リポジトリの clone>` が launchd に毎日 03:00 の実行を登録する。ログは `~/.local/share/curl-backport-proofs/logs/`
- 置き場所: launchd から `~/Documents` の下は読めない（macOS の TCC。exit 126、`Operation not permitted`）。そのため、パイプライン専用の clone を
  `~/.local/share/curl-backport-proofs/src/atrium-lean4`、公開リポジトリの clone を `…/src/curl-backport-proofs`、CompCert/clean を `…/_vendor/certora-clean` に置く
  （`lakefile.toml` の require が5つ上の `_vendor` を指すため）。コードは毎回 GitHub の `auto/pipeline` から pull する。
  スリープ中に過ぎた 03:00 は次に起きたときに1回だけ走り、電源が切れていた日は飛ぶ。未判定の件は次の回に残る
- 途中で止まった回の残り: 次の回の `run.py` が最初に片付け、どれも消さずに残す。プロセスの無い `run.lock` は置き換える、
  commit されていない変更は `git stash`、証明の worktree は `<作業ディレクトリ>/leftover/` に移してブランチを `leftover/…` に改名する。
  ログに `recover:` の行が出る

## 6. この仕組みの限界

- 性質を述べるのも証明するのも Claude である。配布元のものはバックポートだけ
- 外部関数の仕様は仮定である
- `clightgen` の変換は証明の外にある。また、`clightgen` の一部は商用で使えない（`LICENSE-PATH.md`）
