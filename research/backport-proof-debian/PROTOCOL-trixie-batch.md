# 手順書: Debian trixie の curl セキュリティパッチ14件に、上流の修正と同じ証明を付ける

作成: 2026-10-28（証明を試す前に書いた）
判断する人: TK
前提: `PROTOCOL.md` と `RESULTS.md`（CVE-2025-13034 の1件で成功）、`research/c-semantics-link/PROTOCOL.md`（C1 の手順と許す変更）

## 1. 何のためか

使い手は Debian の curl の保守者（Debian Curl Maintainers）。trixie（curl 8.14.1）に当てたセキュリティパッチごとに、
「このバックポートは上流の修正と同じ性質を持つ」ことの Lean の証明を作り、使える形にする。
この手順書は、その証明を作る作業の基準を先に決めておくもの。仮説の検定ではない。

## 2. 対象

salsa.debian.org debian/curl、コミット c2a97b9ea5（debian/trixie、8.14.1-2+deb13u6）の `debian/patches/` にある CVE パッチのうち、
テストと文書を除いて「.c が1ファイル・差分40行以下」の15件から、済んでいる CVE-2025-13034 を除いた14件。選び直さない。

## 3. 1件ごとの手順

1. 上流の修正コミットを特定する（curl.se/docs/CVE-*.html の記載、または Debian のパッチの件名と `Closes #` 番号から）。その親を修正前とする
2. **性質を先に書いてコミットする**: `research/backport-proof-debian/cases/<CVE>.md` に、P1・P0 の文（日本語と Lean の定理の形）と、
   対象の関数、構成（`USE_*` の定義）を書き、証明を始める前にコミットする。このコミットの後で性質を変えたら、そう記録する
3. 4つの翻訳単位を作る（`research/c-semantics-link/case4deb/extract.py` と同じ作り方。関数の本体は原文から機械で切り出す）
   - 上流の修正後（U1）・上流の修正前（U0）
   - 8.14.1 に Debian のパッチを手を加えずに当てたもの（D1）・当てる前の 8.14.1（D0）
4. `clightgen -lean -normalize` で Lean にし、証明する

許す変更は C1 の §4 と同じ（構造体を触るフィールドだけに減らす、マクロの展開、呼ばれる関数は extern にして仕様を仮定する。仕様は弱く書き、強い仕様が要れば記録する）。

## 4. 1件ごとの成功の条件

- **U1・D1**: 修正後の関数（上流・Debian）で、その脆弱性が起きない（P1）
- **U0・D0**: 修正前の関数（上流・8.14.1）で、その脆弱性が起きる入力がある（P0）
- D1・D0 は U1・U0 と同じ形の定理であること。違ってよいのは名前空間、構造体の削減の仕方、外部関数の引数の並び
- 4つすべて成立で、その件は成功
- `sorry`・`admit`・`native_decide`・`bv_decide`・`axiom` の宣言が無い。`#print axioms` は Lean の標準の3つと Certora/clean の外部関数の公理だけ
- 上限: 1件あたり 4時間、`lake build` 80回（C1 と同じ）。超えたらその時点で止め、どこまで示せたかを記録する

性質が Certora/clean の論理で述べられない件（停止しない、メモリの解放の有無、2つの実行の比較が要る、など）は、試す前にその旨を `cases/<CVE>.md` に書いて「対象外」とする。
対象外も件数に数えて報告する。

## 5. 測るもの

- 件ごとの成否、時間、`lake build` の回数、仮定した外部仕様の数
- 上流の証明からバックポートの証明に写したとき、書き換えた行数
- Debian のパッチの「Backported-by」の注記（手で変えた点）が、証明の書き換えに効いたか

## 6. 並列の運用

- 担当 A〜D は、それぞれ別の git worktree（`../atrium-lean4-trixie-<a〜d>`、ブランチ `feat/curl-trixie-<a〜d>`）で作業する
- Lean のファイル名の頭は `Deb<CVE の数字>`（例: `Deb2026_4873After.lean`）。担当どうしで名前が衝突しないようにする
- 結果は担当ごとに `cases/<CVE>.md` の「結果」節に書く。全体のまとめ（`RESULTS-trixie-batch.md`）は、全担当が終わってから書く

## 7. この作業の限界（試す前に書いておく）

- 性質を述べるのも証明するのも Claude である。配布元のものはバックポートだけ
- 外部関数の仕様は仮定である
- 対象は小さな修正だけ。大きい4件は除いている
