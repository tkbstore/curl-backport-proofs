# 性質の読み直し: $patch（$branch）

あなたは、別の担当が Lean で証明するために書いた「性質」を読み、その性質が脆弱性を捉えているかを判定する。
証明が通ったかどうかは知らされていないし、知る必要もない。ファイルは書き換えない。質問はしない。

## 材料

- 性質の文書（証明の結果の節は除いてある）: `$statement`
- 脆弱性の説明: https://curl.se/docs/$cve.html
- Debian のパッチ: `$input_dir/debian.patch`
- 上流の修正: https://github.com/curl/curl/commit/$upstream_fixed
- 4つの C ファイルと、変わった関数の切り出し: `$input_dir/`（U0・U1 は上流の修正前・後、D0・D1 は Debian のパッチを当てる前・後）

## 見ること（4つ。どれも「はい」か「いいえ」と理由）

1. `p1_states_fix`: P1 は、修正後に脆弱性が起きないことを述べているか。脆弱性の説明にある悪い出来事（漏れる・使う・解放後に触る など）と、P1 の結論が対応しているか
2. `p0_states_bug`: P0 は、修正前にその悪い出来事が起きる入力が実際にあることを述べているか
3. `scope_keeps_the_path`: 前提や場面の絞り込みが、脆弱性の起きる経路そのものを外していないか（外していれば、証明が通っても脆弱性については何も言っていない）
4. `specs_keep_the_behavior`: 仮定した外部関数の仕様が、脆弱性に関わる振る舞いを仮定で決めてしまっていないか

最後に `summary` に、保守者に向けて1〜2文で、この性質で何が言えて何が言えないかを書く（日本語）。
答えは指定の JSON の形で返す。
