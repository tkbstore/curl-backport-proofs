# 手順書: H5 の証明を C のコードにつなげられるか

作成: 2026-10-22（試す前にコミットする。結果を見てから基準を変えない）
上流: `context/decisions/0002-ai-vuln-patch-proof-proceed.md`（進む。ただし最初に確かめるのは C の意味論との接続）

## 1. 問い

H5（`research/ai-vuln-verification/RESULTS.md`）では、Claude が C から書き起こした Lean のモデルの上で、5件の修正の性質を証明した。
示していないのは、**実際の C のコードについて同じ性質を証明できるか**である。

この手順書で確かめる仮説:

- **C1**: Claude は、H5 と同じ5件について、curl の修正後の C 関数そのものを Lean に変換し、
  「その脆弱性が起きない」ことを C の意味論の上で証明できる。

## 2. 使う道具（試す前に固定する）

**Certora/clean**（https://github.com/Certora/clean 、ブランチ `feat/c-to-lean`、コミット `123f7f7767e215aceb4821f0d044336d78103ade`、2026-09-08）。

選んだ理由（一次資料 `export/LEAN.md` で確認した範囲）:

- CompCert の `clightgen -lean` が、C の Clight の構文木を Lean 4 として出力する
- Clight の操作的意味論の Lean 4 への移植、それに対して健全性を証明した実行器、分離論理が入っている
- 前提が Lean のまま保てる。VST は Rocq の道具、CN は C 向けの SMT ベースの道具で、どちらも Lean ではない

`export/LEAN.md` が自ら書いている制約（結果の読み方に効くので先に書く）:

- **完全正当性だけ**。停止しないプログラムは対象外（"diverging programs (the logic is total correctness)"）
- **外部関数には仕様が無い**。`malloc`・`memcpy` などを呼ぶコードは、公理化した仕様を与えないと検証できない
- 証明は、ソースの Clight 意味論についての主張である。機械語についての主張ではない
- **ライセンスは CompCert の非商用**（"evaluation, research, educational and personal purposes"）。
  製品に使うには AbsInt の商用ライセンスが要る。この実験は評価・研究なので範囲内。製品化の可否は別に判断する

## 4. 1件ごとの手順と、許す変更

1. 修正コミットとその親コミットから、対象の関数を取り出す
2. 1つの翻訳単位にまとめ、`clightgen -lean -normalize` で Lean に変換する
3. 生成された構文木が変換結果そのものであることを、`rfl` で確かめる（`export/LEAN.md` §7 の例と同じ）
4. 証明する

**関数の本体は変えない**。curl のソースをプリプロセスした結果と、トークン単位で同じでなければならない。

関数の外側で許す変更（すべて記録する）:

- 構造体の定義を、関数が触るフィールドだけに減らす
- マクロを展開する。使わない宣言を消す
- 関数が呼ぶ他の関数は `extern` の宣言にし、Lean 側で仕様を公理として与える

**公理として与えた仕様は、信頼の前提である**。1件ごとに、公理の数と行数を記録する。
仕様は、呼ばれる側の関数の実際の振る舞いを弱めて書く（「何でも返しうる」を既定にする）。
証明を通すために強い仕様を置くことはしない。強い仕様が要る場合は、その旨を記録する。

## 5. 1件ごとの成功の条件

修正後の C 関数について、次の2つを証明する。

1. **P1（C）**: 修正後の関数では、その脆弱性が起きない。H5 の P1 と同じ性質を、C の意味論の上で述べる
2. **P0（C）**: 修正前の関数では、その脆弱性が起きる入力が存在する。
   - 実行器の健全性（`doStep_sound`）を使い、具体的な入力での実行を存在の証拠にしてよい
   - Case 1（停止しない）は、実行器では示せない。修正前の状態が同じ状態に戻ることを示すか、
     それができなければ P0 は不成立とする

満たすべき条件:

- `sorry` と `native_decide` が無い。`bv_decide` も使わない（`export/LEAN.md` の方針に合わせる）
- `#print axioms` が、Lean の標準の3つと、Certora/clean が宣言する外部関数の公理、
  §4 で自分が置いた公理だけ
- 1件あたりの上限: 時間 4 時間、`lake build` 80 回（H5 の2倍。C の意味論の分だけ手間が増えるため）

H5 の P2（関係しない入力では結果が同じ）は、この実験では**求めない**。
2つのプログラムを比べる関係の論理が Certora/clean に無いためである。P2 を試した場合は、参考として記録する。

## 6. 全体の判定

| 成功した件数 | C1 の判定 |
|---|---|
| 3件以上 | **支持** |
| 1件以下 | **棄却** |
| 2件 | **未確認**。H5 の対象23件から、同じ乱数の続き（`random.Random(20261021)` で、既に選んだ5件を除いて5件）を選び、10件で判定する。6件以上で支持、3件以下で棄却 |

数字の根拠は H5 と同じ（RESULTS.md の「全体の判定」）。C の意味論の上での、LLM による証明の成功率は、一次資料で見つけられなかった。
そのため H5 より甘くも厳しくもせず、同じ基準にした。

**道具の問題は別に記録する**。`clightgen -lean` の構築や変換そのものが、環境を整える上限（合計 1 日）の中で動かなかった場合、
C1 の判定は出さず「道具の段階で止まった」と記録する。AI が証明できるかどうかとは別の結果として扱う。

## 8. この実験の限界（判定の前に書いておく）

- 証明する性質（P1・P0 の述べ方）を書くのも、証明するのも Claude である。仕様が弱すぎないことは、P0 で一部だけ担保する
- 外部関数の公理は、curl の他の部分の振る舞いを仮定している。公理が実物と食い違えば、証明は実物について何も言わない
- 対象は5件の小さな修正だけ（H5 と同じ制約を引き継ぐ）
- Certora/clean は自ら「実験的」と書いている。道具の誤りは、差分テスト（`export/LEAN.md` §8）の範囲でしか検査されていない
